## 提案の概要
テスラ車載ブラウザ（クライアント側）に最大約10秒分の先行バッファ（Prefetch Buffer）を保持可能とし、モバイル通信の一時的な悪化・瞬断時に画面停止（フリーズ）を防ぎシームレスに再生を継続できる耐障害アーキテクチャを提案します。
また、将来的な **Intel製MCU（MCU2等）やメモリ制限が厳しい車両への適用** を見据え、クライアント側で保持する最大バッファ量（秒数・メモリ上限）を設定モーダル等から可変調整できる仕組みを導入します。

```text
[ 通信安定時 ]
  Server ──────────────(1.0x リアルタイム配信)──────────────> Client (ローカル最大10秒バッファ維持)
                                                                │
                                                                ▼ Canvas / Web Audio (1.0x PTS 等速再生)

[ 通信悪化・瞬断時 (1〜8秒程度) ]
  Server (WebSocket詰まり/切断)                                Client (一時的オフライン)
    └── PlaybackBuffer にフレーム蓄積 (サーバー側キャッシュ)       └── ローカルバッファから等速再生を継続
                                                                    ★ 画面は一切停止せず再生継続

[ 通信回復時 (バースト急速ダウンロード) ]
  Server ══════════(高速バースト転送: 回線余剰帯域)════════════> Client
  (蓄積フレームを即座に送出)                                      └── ローカルバッファを目標値まで再充電
```

---

## 解決したい課題 / 背景

1. **走行中テスラ車載LTEの瞬断・ハンドオーバー時の画面停止**:
   - トンネル通過、立体交差、基地局切り替えによる数秒間のパケット詰まりや瞬断が発生した際、現状のクライアント側バッファ（ジッター吸収用の数百ms程度）では即座にバッファアンダーラン（画面フリーズ）が発生する。
2. **帯域回復時の未活用**:
   - サーバー側には `PlaybackBuffer`（最大60秒のリングバッファ）が存在するが、回線回復時にクライアントへ余剰帯域を使ってフレームを先読み（急速ダウンロード）し、次の瞬断に備えるパイプラインが常時稼働していない。
3. **MCU世代間のハードウェアリソース格差 (Ryzen vs Intel)**:
   - 現行の AMD Ryzen（MCU3）車はブラウザメモリに十分な余裕があるが、Intel Atom（MCU2など）車両ではブラウザプロセスのメモリ制限が厳しく、過大なバッファを固定で保持すると V8 エンジンの GC 頻発やクラッシュ（ブラウザタブの強制リロード）を招くリスクがある。
   - そのため、固定の10秒ではなく、**ハードウェア性能やユーザー環境に応じてバッファ上限を可変調整（例: 2秒 / 5秒 / 10秒 / オフ）** できる必要がある。

---

## 提案する仕様 / 解決策

### 1. クライアント側先行バッファ (`FramePacer` & `AudioPlayer`)
- **PTS ベースの厳格な 1.0x ペース再生**:
  - クライアント側キューに最大10秒分の未再生フレームが存在していても、早送りにならず `performance.now()` と PTS の差分に基づき等速（例: 30fps）で描画・発音を継続する。
- **A/V 同期 (`AvSyncController`)**:
  - Web Audio API のオーディオコンテキスト時刻をマスタークロックとして映像フレームの描画時刻を調整し、バースト受信中やバッファ再生時も音ズレをゼロに保つ。

### 2. サーバー側バースト送出 & フロー制御 (`PlaybackBuffer` / `WebSocketHandler`)
- **クライアント・バッファ残量フィードバック**:
  - クライアントからサーバーへ現在のローカルバッファ量（例: `bufferedMs: 3200`）と最新描画済みPTSを定期的に通知。
- **動的バースト転送**:
  - 「クライアント側バッファ量 < 目標設定値」かつ「WebSocket の `bufferedAmount` に余裕がある」場合、サーバーはフレーム間の実時間待機を行わず、未送信フレームをネットワーク上限速度でバースト送信し、クライアント側バッファを急速充電する。
  - バッファが目標値に達した後は、通常の 1.0x リアルタイム配信に自動制御する。

### 3. 車両・ハードウェア世代に応じた最大バッファ量の調整機能
- **設定モーダル (Settings Modal) への追加項目**:
  - `バッファリング深度 (Buffer Depth)`:
    - `オフ (超低遅延重視)`: ~0.1秒（従来の 60〜120ms）
    - `軽量 (Intel車 / メモリ節約)`: 2秒（メモリ約 300KB）
    - `標準 (推奨)`: 5秒（メモリ約 750KB）
    - `最大 (耐障害性重視 / Ryzen推奨)`: 10秒（メモリ約 1.5MB）
    - ※ URL クエリパラメータ（例: `?buffer=2s` / `?buffer=10s`）でも初期値上書き可能とする。
- **メモリガード計算と安全機構**:
  - 1000kbps 映像 + 128kbps 音声の場合:
    - 2秒バッファ: 約 282 KB（Intel車載ブラウザでも極めて安全）
    - 5秒バッファ: 約 705 KB
    - 10秒バッファ: 約 1.41 MB
  - クライアント側でメモリ逼迫やフレームドロップを検知した場合、自動的に1段階バッファ深度を下げるセーフガードを設ける。

### 4. 低遅延タッチ操作 (`ACTIVE_INTERACTION`) とのシームレスな両立
- **受動視聴時 (`PASSIVE_STREAMING`)**:
  - 設定された先行バッファ（最大10秒）を維持し、途切れのない動画・音声視聴を最優先。
- **タッチ操作時 (`ACTIVE_INTERACTION`)**:
  - クライアント上でタップ・スワイプ等の入力が発生した瞬間、キュー内の遅延フレームを最新PTSまで即座にパージ（ゼロ遅延ジャンプ）し、50〜80ms の超低遅延操作モードへ移行。
  - 操作終了後、一定時間（例: 5秒間）操作がなければ、バックグラウンドでバースト充電を再開し、自動的にセーフティバッファを再構築する。

### 5. 車載 HUD (Heads-Up Display) 表示の追加
- ストリーミング HUD に現在のバッファ状態を可視化：
  - 例: `BUF: 8.4s / 10.0s (Charging)` または `BUF: 2.0s / 2.0s (Full)`

## 通信プロトコル拡張案 (WebSocket)

### クライアント ➔ サーバー (Control Channel: 0x03 または JSON)
```json
{
  "type": "BUFFER_FEEDBACK",
  "bufferedMs": 4200,
  "targetBufferMs": 10000,
  "maxBufferBytes": 2097152,
  "lastRenderedPts": "1234567890"
}
```

### サーバー ➔ クライアント
- 既存のバイナリ多重化フォーマット（`0x01`: VIDEO, `0x02`: AUDIO）をそのまま使用。
- 既存の WebSocket 送信バッファ監視（High: 768KB, Low: 128KB）と協調してバースト送出。

## 代替案 (Alternatives Considered)

- **サーバー側キャッシュのみで耐える案**:
  - 回線切断時にサーバーに溜めておき、再接続後に再生する方式。
  - 欠点: 瞬断が発生した瞬間に車載画面がいったん停止（スピナー表示やカクつき）してしまい、動画視聴体験が著しく損なわれる。
- **Web Workers / IndexedDB を使った巨大キャッシュ案**:
  - 30秒以上の大容量バッファを IndexedDB や Service Worker に逃がす方式。
  - 欠点: テスラ車載ブラウザのディスクI/Oおよびクォータ制限に抵触する恐れがあり、メモリ内リングバッファ（最大10秒 / 1.5MB程度）で保持する方が圧倒的に高速かつ安全。

## 補足情報・制約事項

- **テスラ車載制約の厳守**:
  - `<video>` タグは絶対に使用せず、既存の `<canvas desynchronized>` + WebCodecs API (`VideoDecoder`) を維持。
- **適用対象**:
  - AMD Ryzen（MCU3）車両: 10秒バッファ推奨
  - Intel Atom（MCU2）車両: 2秒〜3秒バッファ推奨
