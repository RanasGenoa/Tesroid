# 仕様書 04: クライアント映像・音声再生 & A/V 同期

> 関連: PR #114, PR #116, Issue #113, Issue #115

## 1. 概要と目的

テスラ車載 OS の走行時（D/R レンジ）`<video>` 要素強制停止ガードを完全に回避しつつ、単調増加ストリーム世代 ID（`streamEpoch`）と洗練された単一マスタークロック同期アーキテクチャにより、個別の音ズレ回避パッチに依存しない滑らかで低遅延・音ズレのない映像・音声再生体験を実現する。

---

## 2. 機能要件（入力・処理・出力・状態遷移）

### 2.1 映像デコード・キュー分離・ゼロコピー描画
- **描画制約**: 映像描画は常に `<canvas>`（2D コンテキスト `{ alpha: false, desynchronized: true }`）に対して行い、`<video>` 要素の生成・埋め込みはいっさい行わない。デコード済み映像フレームは描画後または破棄時に **100% 解放（`close()`）** し、GPU メモリリークをゼロに保つ。
- **単一 AVCC 仕様**: クライアントとサーバーは常に同一仕様（サーバー側で事前 AVCC 変換済みフレームのみ）で動作し、クライアント側の旧 Annex-B 変換フォールバックは設けない。
- **デコーダ構成プローブ**: H.264（`avc1.<profile><compat><level>` + 4 バイト長プレフィックス形式 `AVCDecoderConfigurationRecord`）に対し、`[hardware + latency] → [hardware] → [latency] → [標準]` の順で構成可能かプローブし、動的な解像度変更時は再構成する。
- **世代 ID (`streamEpoch`) ベースのキーフレームゲート & エラー回復**:
  - 初期状態および新しい `streamEpoch` への切替時は映像・音声双方のデコーダおよびキューを確実に再初期化し、旧 `streamEpoch` のパケットや旧デコーダからの遅延出力を即時破棄する。新 `streamEpoch` では最初のキーフレーム到達までデルタフレームを破棄する。
  - デコーダエラー発生時はデコーダを閉じて再生成し、`150 ms` 後にキャッシュ済み SPS/PPS で再構成した上で、サーバーへ `POST /api/stream/reset` または再同期を要求する（PTS ベースではなく `streamEpoch` で整合性を保証する）。
- **LIVE キューと先読み（CATCHUP）キューの明確な分離**:
  - リアルタイム視聴（`DIRECT LIVE` / `LIVE`）用の最小遅延描画キューと、通信断追っかけ再生（`CATCHUP`）用のバッファ蓄積キュー（目標先行深度 `0〜30 秒`・上限 `48 MiB`、サーバー設定から取得）を責務分離し、通常 LIVE 視聴中に VOD 型の大量 pre-decode 滞留を発生させない。
  - CATCHUP 蓄積キューは上限超過時の破棄を**必ず次のキーフレーム境界までの GOP 単位**（キーフレームが未着の場合は先頭キーフレーム到達まで待機）で行い、`LIVE` 復帰時は蓄積内最新キーフレームへ直接ジャンプする（live-jump flush）。デコード途中のキーフレーム跨ぎ破棄を構造的に起こさない。
  - デコーダ同時投入数はターゲット FPS に応じて上限制御する（30fps 時は `14`、60fps 時は `round(fps / 3)` を `[14, 24]` へクランプ）。

### 2.2 音声デコード・Web Audio 再生
- **デコード & 再生**: Opus 48kHz ステレオ（20ms チャンク）を WebCodecs 音声デコーダで復号し、Web Audio API（`latencyHint: 'interactive'`）で再生する。`f32-planar` およびインタリーブ `f32` の双方を処理し、全 `AudioData` を確実に解放する。
- **アンロック・音量・保護**:
  - PIN キーパッド・接続ボタン・HUD・設定 UI を含む **UI 全域での任意の信頼できるポインタ操作**（document レベル `pointerdown` 捕捉による単一経路）で、オーディオコンテキストを冪等にアンロックする。canvas 等の特定コンポーネント上の操作に限定した解禁経路を持たせず、キーボード操作に依存しない（ブラウザ自動再生ポリシーによりコンテキストはサスペンデッド生成され、解禁されない限り音声クロックが進まない）。
  - 既定音量ゲインは `0.88`（`[0, 1]` クランプ、出力リミッターによる音圧低下防止のヘッドルーム）とし、開始・アンダーラン復帰時に `1 ms` の線形デクリックフェードインを適用する。ミュート時はゲイン `0`・バッファ破棄・新規パケット破棄とする。
  - 音声の再生速度は **常に `1.0x` 固定** とし、ピッチ劣化を伴うタイムストレッチを行わない。
- **ジッタクッション & `streamEpoch` 統合**:
  - 初期再生クッション `160 ms`（+適応遅延）、アンダーラン判定 `> 40 ms` ギャップで `80 ms` 再バッファ、ハードウェア先行スケジュール `25 ms`（最大先行 `500 ms` + 適応遅延）、最大滞留 `45 秒`。
  - スケジュールが先読み上限まで進行した後も、音声 source ノードの再生完了イベントをトリガとする音声供給で自己持続させる（新規デコード出力の到着に依存せず、デコーダ出力が間欠的になってもキュー保持分の再生を無音窓なく継続する）。
  - 同一 `streamEpoch` 内の再送 Opus 設定パケットは冪等に扱い無音ギャップを防ぐ。一方、新しい `streamEpoch` へ切り替わった際は音声デコーダおよびジッタバッファを完全に閉じて再生成し、旧世代の残留音声やブラウザ内部タイムスタンプヘルパーの旧エポックを構造的に遮断する（PTS 比較による後付けストラグラーバリアは不要とする）。
  - **音声先走り保持**: 映像がバッファリング中の間、または音声が映像進行より `8 秒` 超〜`60 秒` 未満先行している間は、音声パケットを退避キューへ保持し映像より先へ再生スケジュールしない（最大滞留 `45 秒`）。音声の stale 破棄は再生地点より `1,500 ms` 超遅れた場合のみ行い、その際は `60 ms` 以内の地点まで一括で再同期する（`1.5 秒` 以下のジッタでは絶対に音声を破棄しない）。

### 2.3 動作モード・適応ジッタ・統一マスタークロック同期
- **状態カプセル化・操作モード切替（単一遷移関数集約）**:
  - クライアントの視聴状態（`STANDBY` / `INTERACTIVE` [旧 `ACTIVE_INTERACTION`・`DIRECT LIVE`] / `LIVE` [旧 `PASSIVE_STREAMING`] / `CATCHUP` / `BUFFER_HOLD`）は、サーバーと共通の排他判別ユニオンおよび **単一純粋遷移関数** にカプセル化する（[03-streaming-transport.md](03-streaming-transport.md) §2.2）。
  - キュー選択（`LIVE` vs `CATCHUP`）、A/V 同期ポリシー、HUD 状態表示（`HOLD` / `DIRECT LIVE` / `WAIT` / `BUF` / `LIVE`）は、複数 boolean の組み合わせ分岐を散在させず、すべて単一状態からの純粋射影（セレクタ）として導出する。
  - タッチ操作時は操作イベント投入により即座に `INTERACTIVE` へ遷移し、最終タッチから **4,000 ms** 経過イベントで `LIVE` へ自動復帰する。
- **適応ジッタバッファ**:
  - 映像到着間隔（`850 ms` 超の瞬断除外）および有効 RTT のばらつき（95%値 − 中央値 `>= 90 ms`）に基づき、目標追加遅延を `60〜240 ms` の範囲で算出し、映像と音声双方へ対称に増減（立ち上がり最大 `20 ms/フレーム`、減衰 `20 ms/秒`）適用する。
- **停滞バッファリング & strict 1x ペース維持**:
  - 到着間隔 `>= 120 ms` かつ転送遅延増大を検知した場合、自己クッションを `+90 ms`（範囲 `180〜450 ms`）拡張し、キュー枯渇時は映像待機（WAIT）状態に入り音声再生を一時保留し（最大待機 `450 ms`）、静穏フレーム継続後に減衰する。
  - 描画スケジュールは**前フレームの予定描画時刻 + 実 PTS 差分**で厳密に計算する（高速再生バースト禁止・倍率 `1.0` 固定）。60fps フレームがバッチ到着した場合も実 PTS のマイクロ間隔を保持し、名目 FPS 間隔へ水増ししない。最小描画間隔 `8 ms` と即描画窓 `now + 2 ms` を守る。
- **PLL マイクロ同期（単一マスタークロックモデル内の連続追従層）**:
  - スピーカーから再生中の音声 PTS に対する目標描画時刻の同期誤差を、毎フレームの**速度微小補正**で吸収する: `45 ms` 以内（lip-sync 知覚限界）は何もしない（ハンチング防止）、`45〜150 ms` は比例ゲインにより毎フレーム最大 `±0.75 ms` のシフト、`150 ms` 超は大ズレ安全網としてスルーレート `±2.0 ms/frame` へ厳格クランプし等速性を保ちながら吸着する。
  - WAIT（音声到達待ち）・後方フレームの DROP・`1,500 ms` 超でのライブエッジ再アンカーは大ズレの安全網として維持するが、`150 ms` 未満の通常ドリフトは**フレーム破棄・音声再バッファなしに速度補正のみで収束**させなければならない。
- **洗練された単一マスタークロック同期アーキテクチャ（個別条件分岐パッチの廃止・統合）**:
  - サーバー側エンコーダも単一マスタークロック基準＋`streamEpoch` で映像・音声タイムスタンプを同期採番する。
  - **メイン（プライマリ）セッションの音声実再生時刻** を絶対的マスタークロックとする（セカンダリ端末はプライマリ基準 PTS へ追従・同期のみ）。音声アンカーからの線形外挿は有効窓を持ち、最終アンカーから `1.5 秒` 超の外挿は idle（未再生）として扱い、`10 秒` 以上古いアンカーは破棄する（外挿倍率は常に `1.0x`）。
  - 個別の音ズレ閾値ごとの条件分岐パッチ（`60ms` 特別ゲート、`800ms` 上流トリム、`2.5s` 窓連続 no-op エスカレーション等）を廃止し、**常に音声マスタークロックを基準として映像フレームの描画時刻計算・追従（PLL）・遅延フレーム破棄を統一的に評価する単一同期モデル** へ統合する。
  - **達成すべき品質目標（PR #114 / #116 由来要件の昇華）**:
    - `DIRECT LIVE -> LIVE` 切替や通信停滞復帰後においても、音声再生を途切れさせることなく映像側同期機構のみで **復帰後 4 秒以内に `|音ズレ| <= 60 ms`** へ収束させ、その後 8 秒以上の観測でも過補正・ハンチングを起こさない（正常な 1x 到着および音声遅れ側には不必要に干渉しない）。
    - 先読み蓄積等により持続的な音声先行で映像側単独では収束不能な状態に陥らないよう、キュー分離設計および必要時のプライマリ起点 `POST /api/stream/reset`（`streamEpoch` 更新）で確実にライブエッジへ復帰する（セカンダリからのリセット要求は不可）。
  - **正確なドリフト計測 & ドロップ計上**:
    - 5 秒超過時の相対計算フォールバックおよび 2 秒超過時の 0 リセット（異常隠蔽）を廃止し、**符号付きの真の A/V ドリフト** をそのまま算出・報告する。
    - 同期維持のために映像側で破棄されたフレームは、すべて例外なく **ドロップフレーム数（メトリクス）へ計上** する。

## 3. 非機能要件・制約条件

- **D レンジ再生継続保証**: クライアントのソースコードおよびビルド後 HTML のいかなる箇所にも `<video>` タグの記述・動的生成を含めてはならない。
- **GPU リソース 0 リーク**: 描画・破棄・リセットの全経路で、取得した映像/音声デコードオブジェクトを漏れなく解放すること。
- **音声品質優先**: 音ズレ吸収のために音声のピッチ変更や頻繁な無音切断を行わないこと。
- **負荷保護の役割分担**: 車載端末（MCU2 等）の処理能力不足による 60fps 処理落ちに対しては、ユーザー側でプロファイル・FPS 設定を選択して対応する方針とし、システム側の自動 FPS 降格は行わない。

## 4. 判明しているエッジケースとエラー時の振る舞い

1. **デコーダ未構成・クローズ状態でのパケット到着**: 例外を送出せず安全に破棄する。
2. **旧 `streamEpoch` パケット・遅延非同期デコード出力の到達**: `streamEpoch` 不一致またはデコーダ世代不一致として即座に破棄し、音声クロック・映像キューを汚染しない。
3. **静止画での無通信誤認**: 静止画で映像パケットが間欠停止しても、音声が正常に流れている間はネットワーク停滞によるバッファリングへ誤遷移しない。
4. **40ms 未満の音声ジッタ**: 一過性の微小到着揺らぎでは音声アンダーランと判定せず、不要な再バッファやアンカー破棄を起こさない。
5. **5 秒超の巨大 A/V ドリフト**: 丸めや 0 リセットを行わず真のドリフト値として正確に検知・報告する。

## 5. 受け入れ条件（テスト観点）

- **AC-01 (車載ブラウザ制約・AVCC 単一入力・GPU メモリ解放)**:
  - **Given** ビルド済みクライアントおよび稼働中の再生パイプライン
  - **When** ソースコード・出力 HTML の検査、および AVCC フレームの連続描画・破棄・リセットを実行する
  - **Then** `<video>` 要素は 0 件で `<canvas>` が存在し、全フレームがゼロコピー投入され 100% 解放（`close()`）されている。
- **AC-02 (`streamEpoch` による境界保護とキーフレームゲート)**:
  - **Given** `streamEpoch = E` で稼働中の映像・音声再生パイプライン
  - **When** 初期化直後にデルタフレームを受信する／`POST /api/stream/reset` 等で `streamEpoch = E+1` へ遷移し直後に旧 `E` の遅延パケットが届く
  - **Then** 新世代の最初のキーフレームまでデルタは破棄され、旧世代 `E` の映像・音声パケットはデコード前後に無条件破棄されて音ズレや無音・無限 WAIT を起こさない。
- **AC-03 (キュー分離 & 音声アンダーラン保護・音圧維持)**:
  - **Given** LIVE キューと CATCHUP 蓄積キューが分離された再生パイプライン
  - **When** 通常 LIVE 視聴を行う／40ms 未満の音声揺らぎが発生する／同一 `streamEpoch` の Opus 設定が再送される／デコーダ出力が一時的に止まる
  - **Then** 通常 LIVE 中に不必要な大量 pre-decode 滞留が積まず、微小揺らぎで音切れせずゲインも維持され、同一世代の設定再送では無音ギャップが発生せず、デコード出力が止まってもキュー保持分の再生は完了イベント起点の音声供給により無音窓なく継続する。
  - **And** 初回操作が PIN キーパッドまたは HUD 上のタップであった場合でも、追加の canvas 操作を待たずに音声再生が開始する（音声関連テレメトリに解禁失敗が残らない）。
- **AC-04 (統一マスタークロック同期と 4 秒以内収束)**:
  - **Given** メイン（プライマリ）音声をマスタークロックとして再生中のクライアント（および追従中のセカンダリ）
  - **When** `DIRECT LIVE -> LIVE` 復帰・2 秒瞬断バースト・大ズレ（`1,500 ms`）からの復帰を実行する
  - **Then** 音声再生（`1.0x`）を止めずに映像側同期のみで 4 秒以内に `|音ズレ| <= 60 ms` へ収束し、その後 8 秒間再拡大せず、同期のために破棄した映像フレームはすべてドロップ数へ計上される。
- **AC-05 (真のドリフト観測)**:
  - **Given** 映像と音声に `5,000 ms` を超えるズレが存在する状態
  - **When** ドリフト計測値を取得する
  - **Then** 相対計算や `0 ms` への隠蔽リセットを行わず、符号付きの真のドリフト値が報告される。
- **AC-06 (strict 1x ペーシングと PLL マイクロ同期)**:
  - **Given** 音声マスタークロックに同期中の再生パイプライン
  - **When** 60fps フレームがバッチ到着する／`45〜150 ms` の持続ドリフトが発生する／`45 ms` 以内の微小ドリフトが発生する
  - **Then** 描画間隔は実 PTS 差分に従いバースト・名目間隔への水増しは起きず、`45〜150 ms` のドリフトは毎フレーム `±0.75 ms` 以下の速度補正のみでフレーム破棄・音声再バッファなしに収束し、`45 ms` 以内では一切の補正操作（ハンチング）が発生しない。

## 6. 要確認事項

- **音声マスタークロック停止時の映像低 FPS**（2026-11-28 テレメトリ実測）: AudioContext が未解禁で音声クロックが凍結した状態では、符号付きドリフトが単調増大し `video_long_wait` が連続する（ライブエッジ再アンカーの描画継続は有効に動作するが実効 FPS は低い）。§2.2 の UI 全域解禁条項明確化で解消されるため、修正版で同状態が観測されなければクローズ。再発時はクロック停滞検知の要否を確認する。
