# 仕様書 03: ストリーミング転送・WS プロトコル・輻輳／バッファ制御

> 関連: Issue #104

## 1. 概要と目的

単一の WebSocket（WSS）接続上で映像・音声・タッチ入力・制御・計測データを低遅延で多重転送し、トンネルや地下駐車場などの一時通信断（最大 30 秒）および狭帯域モバイル LTE 回線の輻輳環境下でも、明示的なストリーム世代 ID（`streamEpoch`）を中核とした一貫した状態管理により、破綻や恒久的な音ズレを起こさない安定した追っかけ視聴と自動復旧を実現する。

---

## 2. 機能要件（入力・処理・出力・状態遷移）

### 2.1 単一多重化バイナリ WebSocket プロトコル & 単調増加世代 ID (`streamEpoch`)
- **接続仕様**: 単一エンドポイント `/ws`（バイナリ `arraybuffer`、ソケット `TCP_NODELAY` 有効）。
- **最重要仕様 — 単調増加ストリーム世代 ID (`streamEpoch`)**:
  - サーバーは配信セッション開始・再起動・同期リセット・電源復帰のたびに **1 ずつ単調増加する符号なし 32bit 整数 `streamEpoch`** を発行する。
  - すべてのメディアパケットおよびストリーム状態制御メッセージへ最新の `streamEpoch` を付与する。
  - クライアントおよびサーバーの送信キューは、現在有効な `streamEpoch` と一致しない旧世代の映像・音声パケットを検知した時点で **即時破棄** し、PTS 比較による後付けバリアなしに世代跨ぎの古い音声・映像混入を構造的に遮断する。
- **チャンネル ID（先頭 1 バイト）**:
  - サーバー → クライアント: `0x01`（映像）、`0x02`（音声）、`0x03`（制御応答 JSON）
  - クライアント → サーバー: `0x10`（タッチ入力）、`0x11`（リサイズ）、`0x12`（認証）、`0x13`（制御コマンド JSON）、`0x14`（品質メトリクス JSON）、`0x15`（詳細テレメトリ JSON、最大 `512 KiB`）
- **メディアフレーム形式（`0x01` / `0x02`、最小 14 バイト）**:
  - `[Channel: 1B][Flags: 1B][streamEpoch: 4B UInt32BE][PTS: 8B Int64BE (µs)][Payload: NB]`
  - 映像フラグ: `KEYFRAME (0x01)`, `CONFIG (0x02)`, `AVCC (0x04)`
  - 音声フラグ: `KEYFRAME (0x01)`, `CONFIG (0x02)`
- **リサイズ通知（`0x11`、7 バイト）**:
  - `[0x11][幅: UInt16BE][高さ: UInt16BE][DPR×100: UInt16BE]`
  - クライアント側デバウンス `350 ms`、サーバー側デバウンス `400 ms`（プライマリのみ有効）。
  - 幅 `1000 px` 未満時は DPR（未指定・`<= 1` 時は `1.35`）を `[1.25, 1.5]` へクランプしてスケーリングし、設定最大辺（`640〜1920`、既定 `1280`）以下に収めた上で、幅を 8 ピクセル境界（`& ~7`、下限 `640`）・高さを 2 ピクセル境界（`& ~1`、下限 `360`、上限 `min(1080, maxSize)`）へアライメントする。実車利用ではナビ等と並べた小窓表示（代表基準 `773×553 CSS / DPR 1.53`）を主対象とし、将来のファームウェア更新に伴う DPR 変化は `1.53` 等の固定値直書きを行わずクライアント物理ピクセルと本リサイズ計算で吸収する。
- **タッチ入力パケット（`0x10`、33 バイト固定）**:
  - `[0x10][type=2: 1B][action: 1B][pointerId: 8B Int64BE][x: 4B Int32BE][y: 4B Int32BE][screenW: 2B][screenH: 2B][pressure: 2B][actionButton: 4B][buttons: 4B]`
  - action 定義: `DOWN=0, UP=1, MOVE=2, CANCEL=3, POINTER_DOWN=5, POINTER_UP=6`。

### 2.2 ストリーミング状態のカプセル化と単一遷移関数（スタブ先行設計）
- **排他的 5 状態の判別ユニオン定義（Illegal States Unrepresentable）**:
  - セッションの配信・視聴状態は複数の独立した boolean フラグ（`isLive`, `isCatchup`, `isStandby`, `isInteractive`, `isHolding` 等）で分散保持してはならず、以下の排他的な単一状態（判別ユニオン）としてカプセル化する。
    - **`STANDBY`**: 非配信・待機中（未接続・後席待機 `SECONDARY_STANDBY`・電源スリープ `SLEEP_PAUSED`）。メディア送出・入力注入・バッファ蓄積をすべて抑止する。
    - **`INTERACTIVE`**: ユーザー操作直後の超低遅延モード（操作から `4,000 ms` 未満）。進行中の `CATCHUP` キューは即破棄し、ライブエッジ最小遅延配信を行う。
    - **`LIVE`**: 通常リアルタイム視聴（`LIVE` 経路およびビットレート連動ヒステリシスのみを適用し、ソケット輻輳で `CATCHUP` へ遷移しない）。
    - **`CATCHUP`**: 通信断またはアイドル復帰からの追っかけ視聴（リンク認識フロー制御で排水し、完了で `LIVE` へ遷移する）。
    - **`BUFFER_HOLD`**: リングバッファ未消費占有率 `>= 85%` 到達によりサーバー生成を `0.0x` に停止した状態（クライアント未接続時や極端な滞留時のリングバッファ溢れ・送出漏れを防止する）。既生成バッファの再接続クライアントへの送出（`CATCHUP` 排水）は抑止せず、未消費占有率 `<= 10%` への排水、または `USER_INTERACTION`・`STREAM_RESET`・別プライマリによるセッション奪取（`4009`）で即座に解除される。
- **単一遷移関数契約（Stub-First）**:
  - 状態遷移の判定・更新は **1 つの純粋遷移関数** `transitionStreamingState(state, event) => { nextState, effects }` に完全集約する。
  - 周辺モジュール（WS ハンドラ、タイマー、入力注入、電源連携、クライアント描画・HUD）は遷移条件を独自に評価してはならず、**イベント投入** と **返却された宣言的 `effects` の実行**、および **状態モジュールが提供する純粋セレクタ参照** のみを行う。
  - 実装着手時は周辺コードより先に、状態型・イベント型・副作用型・網羅性チェック（`assertNever`）を備えた単一遷移関数のスタブおよび状態遷移表を先行定義する。

### 2.3 LIVE 配信のバックプレッシャー制御（ビットレート連動ヒステリシス）
- **水位算出（正典）**: 配信ビットレート設定（`bps`）に連動した二段階水位を唯一正典とする。
  - `高水位 = clamp(round((bps / 8) * 3.0), 512 KiB, 1536 KiB)`
  - `低水位 = max(96 KiB, round(高水位 * 0.2))`
- **状態遷移**:
  - プライマリ・セカンダリそれぞれのソケット送信キュー残量（`bufferedAmount`）が独立に高水位を超過した場合、当該ソケットのみ GOP ドロップモードへ遷移し映像フレーム送出をスキップする。
  - 送信キュー残量が低水位以下へ減少し、かつ **新しい IDR キーフレームが到達した場合のみ** 当該ソケットの通常配信へ復帰する。
  - 音声パケットは GOP ドロップの対象外とし、ソケット残量 `2 MiB` 以下で送信する。
- **不変条件**: LIVE 配信中のソケット輻輳では絶対に追っかけ（`CATCHUP`）モードへ遷移させず、ヒステリシスによる GOP スキップのみへ一元化する。

### 2.4 統合バッファ・追っかけ（CATCHUP）・生成一時停止（Buffer-Hold）制御
ユーザー体験（通信断や狭帯域でも途切れず、復帰後は滑らかに追いつき、過大な滞留時にはサーバー生成を一時停止して追従させる）として、リングバッファ・CATCHUP・リンク認識制御・生成一時停止を単一のシームレスなモデルとして統合する（電源・タイマー排他・スリープ遷移は [10-power-lifecycle.md](file:///Users/takumi/Desktop/Tesroid/docs/specs/10-power-lifecycle.md) へ集約）。

- **サーバー側リングバッファ（60 秒 / 48 MiB）**:
  - 保持時間既定 **60 秒**（`PLAYBACK_BUFFER_SECONDS`）・メモリ上限既定 **48 MiB**（`PLAYBACK_BUFFER_MAX_BYTES`）。
  - 設定パケット（`CONFIG`, `PTS=0`）はフレーム列へ混入させず専用メタデータとして別保持する。
  - 上限超過時は最古の完全 GOP 単位とそれに先行する音声を破棄する（進行中の最後の 1 GOP は保持）。
  - ストリームリセット、スリープ移行、新規プライマリ切替、エンコード寸法変更、ナビゲーション/再起動時はバッファを全消去し、`streamEpoch` を進める。
- **シームレスな追っかけ（CATCHUP）開始・配送制御（関連: Issue #104）**:
  - プライマリがアイドル視聴状態（最終操作から `IDLE_TO_BUFFER_SECONDS` 既定 `5 秒` 超）から再接続し、サーバー設定の目標バッファ深度 `targetBufferMs`（`[0, 30000] ms`、既定 `10,000 ms`）のもとで同一 `streamEpoch` 上の有効確認済み PTS が存在する場合、直前キーフレーム（最古から 5 秒以内まで許容）から追っかけ配信を開始する（実効ウィンドウ下限 `400 ms`）。
  - **リンク認識フロー制御（名前付き定数による固定値定義・後続チューニング対応）**:
    - プライマリの再生進捗（有効サンプル窓 `250 ms〜5,000 ms`、進捗レート `[0, 20]`）から実効排水レート（EWMA `0.7 * prev + 0.3 * rate`）を推定する。
    - 排水レート `< 0.85x`（定数 `DRAIN_RATE_CONGESTION_THRESHOLD`）または連続ソケット詰まり `>= 3` 回の輻輳リンク時のみ、実効ウィンドウを `min(targetBufferMs, max(2500 ms, round(targetBufferMs * rate)))` へ縮小し、ソケットガードを `128 KiB → 32〜64 KiB`、バースト間隔を `2 ms → 10 ms` へ緩和して自己輻輳（bufferbloat）を防ぐ。健全リンクでは `128 KiB / 2 ms` を維持する。
    - 25〜30 秒のトンネル復旧は無欠落で保護しつつ、`max(2 × 目標バッファ, 30 秒)` を超える無限滞留時は最古 GOP を間引く（キュー絶対上限 `6,600` フレーム）。
  - **自動遷移**: キュー排水完了で即 `LIVE` へ遷移する。ユーザー操作・配信リセット要求・画面遷移・リサイズ時は即座にキュー破棄し新 `streamEpoch` で `LIVE` へ戻る。
- **統合された生成一時停止（Buffer-Hold）連携**:
  - 主目的を「クライアント未接続時および極端な滞留時のリングバッファ溢れ・送出漏れ防止」とし、指標はリングバッファ（`60 秒` / `48 MiB`）の **未消費占有率 `max(未消費時間 / 60s, 未消費バイト / 48MiB)`** のみに固定する（可変閾値は持たない）。
  - **発動条件**: 未消費占有率（静止画中に壁時計膨張させないようリングバッファ最新メディア PTS 基準）が **`>= 85%`** に達したら、`BUFFER_HOLD` 状態へ遷移してブラウザ（`SIGSTOP`）とエンコーダを停止し、サーバー生成を `0.0x` へ落とす。
  - **生成停止と送出継続の分離**: `BUFFER_HOLD` はサーバー側の **生成停止** のみを意味し、再接続したクライアントへの既生成バッファ送出（`CATCHUP` 排水）は抑止しない（送出抑止セレクタ `shouldSuppressMediaSend` は `STANDBY` のみ `true`、生成停止セレクタ `shouldPauseGeneration` は `STANDBY` と `BUFFER_HOLD` で `true`）。
  - **再開条件**: クライアントへの送出により未消費占有率が **`<= 10%`** まで排水されたら `ACTIVE`（生成再開）へ自動復帰し、新 `streamEpoch` でライブ配信を再開する。
  - **例外的な即復帰**: `USER_INTERACTION`、`STREAM_RESET`、または別プライマリによるセッション奪取（`4009` / ライブ端転落）時は未消費バッファを破棄して即 `ACTIVE` へ復帰する。
  - Hold 期限タイマー・自動スリープ排他・`autoSleepMinutes = 0` 時の期限再武装・手動停止変換はすべて [10-power-lifecycle.md](file:///Users/takumi/Desktop/Tesroid/docs/specs/10-power-lifecycle.md) で一元管理する。

### 2.5 ライブ同期・配信リセット（`POST` への完全一本化）
- **単一リセット API（REST `POST` 統一）**:
  - 従来の複数の LIVE ジャンプ・エンコーダ再起動経路（WS コマンド群＋スキップ付き REST API）を廃止し、**単一の `POST` エンドポイント（`POST /api/stream/reset`、プライマリ認証必須）** へ統一する。
  - 「健全 LIVE 時の全体再起動スキップ」仕様は **完全に削除** する。`POST /api/stream/reset` が呼ばれた場合、サーバーは状態にかかわらず **常に映像・音声双方のエンコーダおよびクライアント側の映像・音声デコーダを完全にリセット** し、リングバッファ・送信キューを破棄して新しい `streamEpoch` を発行した上でクリーンなライブ配信を開始する。

### 2.6 RTT 鮮度管理 & 統一バッファ計測
- **PING / PONG**: クライアントは `1,000 ms` ごとに `PING` を送信し、サーバーが `PONG`（最新メディア PTS、モード、バッファ残量、プライマリ基準 PTS 等）を返す。
  - サーバー残量算出はクライアントの映像・音声双方の滞留を考慮した `max(0, serverLagMs - max(clientVideoBufferedMs, clientAudioBufferedMs))`（`serverLagMs` は最新メディア PTS 基準）を用いる。
- **RTT 鮮度**: クライアントの瞬間 RTT（EWMA `0.7 * prev + 0.3 * raw`、最小値履歴窓 8）は LIVE かつキュー滞留ゼロ時のサンプルのみで更新し、有効計測から **5 秒超過** した場合は鮮度切れとして破棄（`0` / `接続中`）する。
- **統一フィードバック**: クライアントは `250 ms` ごと（またはフレーム進行・滞留変化 `>= 250 ms` 時）に映像・音声双方の滞留量を報告し、サーバーは `max(PTS 差分, 映像滞留, 音声滞留)` を用いてフロー制御する。

## 3. 非機能要件・制約条件

- **単一接続原則**: 動画・音声・操作・テレメトリを単一の WSS 接続上で多重化すること。
- **無欠落耐性**: 60fps 映像 + 50pps 音声環境での 25〜30 秒間通信途絶からの復帰時（最大 6,600 フレーム、48 MiB）に GOP 途中破棄を起こさないこと。
- **ビット完全対称性**: メディアパケットヘッダ（Channel・Flags・`streamEpoch`・PTS）のバイナリレイアウトをクライアント・サーバー間で完全一致させること。

## 4. 判明しているエッジケースとエラー時の振る舞い

1. **旧 `streamEpoch` パケットの遅延到着**: ネットワーク経路やクライアントキューに残留していた古い世代の映像・音声パケットが到着しても、`streamEpoch` 不一致により即座に破棄し A/V ズレやデコーダ汚染を起こさない。
2. **不正・切り詰めバイナリメッセージの受信**: 最小長未満または不正 JSON の制御コマンドは無視して例外で接続やサーバーを落とさない。
3. **目標バッファ `0 ms` 設定時**: CATCHUP ウィンドウに下限 `400 ms` を保証して送出停止を回避する（Buffer-Hold は固定のリングバッファ占有率 `85%` / `10%` で動作する）。
4. **テレメトリペイロード肥大**: クライアントから `512 KiB` を超えるテレメトリフレームを受信した場合は即座に破棄する。
5. **静止画連続時の未消費滞留誤判定防止**: 画面変化がなく映像フレームが生成されない間も壁時計ベースで未消費滞留を膨張させず、リングバッファ上の最新メディア PTS を基準に滞留量を算出する。

## 5. 受け入れ条件（テスト観点）

- **AC-01 (プロトコル対称性 & `streamEpoch` 排他)**:
  - **Given** `streamEpoch` を含む映像・音声・制御・タッチ・リサイズ各パケット
  - **When** エンコード/デコード往復、および `streamEpoch` 更新後に旧世代パケットを投入する
  - **Then** バイナリレイアウトはビット完全一致し、旧世代の映像・音声パケットはデコードおよび再生へ一切投入されず即時破棄される。
- **AC-02 (ビットレート連動 LIVE ヒステリシス & セカンダリ分離)**:
  - **Given** 設定ビットレートに基づく高水位・低水位で運用中のプライマリおよびセカンダリ接続
  - **When** プライマリに単発 IDR バーストが起きる／セカンダリのみ高水位を超過する／プライマリが高水位超過後に低水位+キーフレームで回復する
  - **Then** 単発 IDR ではドロップせず、セカンダリ輻輳はプライマリへ影響せず、プライマリ輻輳は CATCHUP 遷移せず低水位+キーフレームで即時復帰する。
- **AC-03 (リングバッファ・リンク認識 CATCHUP・Buffer-Hold 統合)**:
  - **Given** 60 秒/48 MiB リングバッファとリンク認識定数パラメータを備えた配信パイプライン
  - **When** 25〜30 秒通信断から復帰する／低排水レート `< 0.85x` や詰まり 3 回以上が起きる／リングバッファ未消費占有率 `max(時間/60s, バイト/48MiB)` が `>= 85%` に達し、再接続後に `<= 10%` まで排水される（または操作・リセット・4009 奪取が起きる）
  - **Then** 25〜30 秒復旧は無欠落、輻輳リンク時は窓縮小・ガード 32〜64KiB 化・10ms 緩和が発動、Hold 発動で生成のみ `0.0x` 停止しつつ既生成バッファの CATCHUP 送出は継続し、`<= 10%` 排水（または操作・リセット・4009 奪取による即復帰）で生成を自動再開する。
- **AC-04 (`POST /api/stream/reset` による完全リセット一本化)**:
  - **Given** 正常配信中・CATCHUP 中・Hold 中のいずれかの配信状態
  - **When** プライマリから `POST /api/stream/reset` を呼び出す
  - **Then** スキップ判定は行われず常に映像・音声双方のエンコーダおよびデコーダがリセットされ、新 `streamEpoch` でクリーンな LIVE 配信が再開する。
- **AC-05 (RTT 鮮度 & 映像/音声滞留反映)**:
  - **Given** 接続中のクライアント
  - **When** 5 秒間有効 PONG が途絶える／音声滞留が映像滞留を上回る
  - **Then** RTT は 5 秒超過で鮮度切れ破棄（`接続中`）となり、PONG 残量およびフロー制御に音声滞留を含めた実効値が反映される。
- **AC-06 (ストリーミング状態カプセル化 & 単一遷移関数不変条件)**:
  - **Given** `STANDBY` / `INTERACTIVE` / `LIVE` / `CATCHUP` / `BUFFER_HOLD` を表現する単一純粋遷移関数と純粋セレクタ（`shouldSuppressMediaSend`, `shouldPauseGeneration`）
  - **When** `LIVE` 中のソケット輻輳、`CATCHUP` 中のユーザー操作、`STANDBY` 中のメディア・操作イベント、`INTERACTIVE` の `4,000 ms` 経過、`BUFFER_HOLD` 中の CATCHUP 再接続・排水・操作・手動停止・リセットを順次投入する
  - **Then** すべての遷移が単一遷移関数のみで決定論的に解決され、`LIVE` 輻輳では `CATCHUP` へ遷移せず、`CATCHUP` 中の操作は即 `INTERACTIVE`（`CATCHUP` キュー破棄＋新 `streamEpoch`）へ遷移し、`STANDBY` では送出・生成・操作がすべて抑止され、`BUFFER_HOLD` は生成停止を維持したまま CATCHUP 送出を継続し、`INTERACTIVE` は `4,000 ms` 経過で `LIVE` へ自動復帰する。
